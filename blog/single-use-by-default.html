Single-use by default: authority that cannot be replayed

A grant that can be presented twice is a grant you have already lost control of. Binding one nonce to one action, consumed exactly once, makes replay a refused event instead of a silent success.

Reusability is a virtue almost everywhere in software — and a liability in authorization. A token you can present again is a token that can be captured, delayed, and replayed. A grant that survives its first use is authority still sitting on the table after the action it was meant for is done. The safe default for consequential authority is the opposite of reusable: single-use, bound to one action, consumed exactly once.

Replay is the quiet failure

The dangerous thing about replay is that nothing looks wrong. The signature verifies. The scope matches. The action is one the holder is genuinely allowed to perform. The only anomaly is that it happened again — and a system that only checks “is this valid?” has no way to notice. Duplicate delivery, a retried request, a captured grant re-sent by an attacker: to a stateless validator they are all the same legitimate-looking call.

Making authority single-use turns that quiet failure into a loud, refused event. Each grant carries a nonce. Before the protected path acts, it atomically reserves that nonce in a consumption ledger. The first presentation wins the reservation and proceeds; every later presentation of the same nonce loses the race and is refused as replay. “Exactly once” stops being a hope about the network and becomes a property the system enforces.

Invariant

One grant, one nonce, one action. Reserved-or-refused, atomically. A second presentation of a consumed nonce is a refusal — never a second execution.

What single-use is honest about

We are careful here. A browser demonstration can show one-winner selection as a reference; it does not prove distributed linearizability under partition. Real single-use at scale is a property of a deployed ledger with a genuine consistency story, and we mark that as target work rather than claim it is solved by a client-side demo. The design principle, though, holds regardless of maturity: authority should be spent, not held.

Why default matters

Plenty of systems could issue single-use credentials and simply don't, because the reusable path is more convenient and the risk is invisible until it isn't. As more actions are taken by software that retries aggressively, delegates freely, and runs unattended, the cost of reusable authority stops being theoretical. Designing single-use as the default — the thing you opt out of, not into — is how you keep replay from being a latent liability you discover during an incident.
