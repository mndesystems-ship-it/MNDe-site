The execution gap: “it had permission” is the wrong question

When something goes wrong, the reassurance is almost always the same: the agent had permission. That sentence is true and beside the point. Permission is a broad, ambient, durable claim. Execution is a single specific act. The distance between the two is where unintended actions live.

Two different kinds of statement

"Has permission to merge pull requests" and "is authorized to merge this pull request, at this commit, into this branch, right now" are not the same statement at different resolutions. They are different kinds of statement. The first is a standing property of the actor. The second is a fact about one act. Most systems only ever check the first, then let the actor choose the second for itself.

For a human that delegation of choice is reasonable; judgment lives with the person. For an automated agent, "choose the specific act for yourself" is precisely the latitude you did not mean to grant. The permission was meant to describe a boundary. The agent treats it as a blank check inside that boundary.

The gap is structural, not a bug

This is not a matter of a missing check that a diligent team would have added. It is built into the shape of permission-based access. A permission has to be broad enough to cover the class of actions you want to allow, which means it is necessarily broader than any one action inside that class. The gap between "the class is allowed" and "this instance was intended" cannot be closed by making the permission more careful. It can only be closed by checking the instance.

Authorize the act, at the act

Closing the execution gap means moving the decision to the moment and the granularity of the act itself. Instead of asking, once and in advance, "may this agent merge pull requests," the system asks, at the point of execution, "is there valid authority for exactly this merge?" The authority is scoped to the specific parameters — repository, pull request, expected commit, method — and it is checked against the action actually being attempted. If the action drifts from what was authorized, even by one field, it is a different action, and the authority does not cover it.

No consequential machine action executes unless it presents valid, specific, unconsumed authority for that exact action.

What this does and does not buy you

Done well, this makes "it had permission" unsayable, because there is no ambient permission to point to — only a grant for the exact act, which either matched or did not. What it does not do by itself is prevent an authorized decision from being a bad one; authorizing the exact act is a control over scope, not over judgment. Deciding whether to issue a grant is a separate, policy-level question, and one we treat as its own boundary rather than folding into execution.

We describe the enforcement point — a protected executor that will not act without a valid grant — as a reference implementation today, with provider-enforced non-bypassability as target architecture. The distinction matters, and we keep it visible: the model is only as good as the point that actually refuses.
