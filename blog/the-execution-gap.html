The execution gap: “it had permission” is the wrong question

A standing permission is a broad, ambient claim. Execution is a single, specific act. The interesting — and increasingly dangerous — engineering lives in the distance between them.

When something goes wrong with an automated action, the first question in the incident review is almost always: did it have permission? And the honest answer is almost always yes. The credential was valid. The scope covered the operation. By the rules of the system, nothing was violated. That is precisely the problem. “It had permission” describes a broad capacity to act. The incident is about one specific act. Those are not the same object, and treating them as the same is where the risk hides.

Two different things wearing the same word

A permission is a standing, ambient property: a role, a scope, a token that remains true across many actions and much time. An execution is a point event: this call, these exact parameters, this moment. Classic access control checks the standing property and then lets an unbounded number of point events flow underneath it. Between the check and the act, anything the scope permits is fair game — including things no operator would have approved if asked about them one at a time.

We call that space the execution gap. It is not a bug in any particular system; it is a structural consequence of authorizing capacity instead of acts. When a human held the credential and clicked once, the gap was small and a person's judgment sat inside it. When software holds the credential and acts thousands of times unattended, the gap is where mistakes, confusion, and abuse compound silently.

The reframe

Stop asking whether the actor had permission. Ask whether this exact action presented valid, specific, unconsumed authority at the moment it executed. If it did not, it does not run.

Closing the gap

The execution gap closes when authority is evaluated at the act, not upstream of it. Concretely that means an action carries a grant bound to its exact parameters; a protected path validates and atomically consumes that grant before it does anything consequential; and the decision is recorded as evidence. The check is no longer “is this actor allowed things like this?” but “is this the authorized action, and has it already been spent?”

The parts of this that are demonstrable today — canonical parameter binding, exact-action grants, refusal on mismatch — we ship and let you run. The parts that depend on a real deployment enforcing non-bypassability, we label as target architecture rather than claim. The discipline is the same either way: narrow the window in which capacity substitutes for a decision.

Why this pressure keeps rising

Every increment of autonomy widens the execution gap. More actions per credential, more delegation between principals, fewer humans positioned to catch the wrong last mile. We don't think the answer is to slow autonomy down — it is genuinely useful. We think the answer is to make the moment of execution the place where authority is proven, so that scaling the number of actions does not mean scaling the amount of unchecked trust.
